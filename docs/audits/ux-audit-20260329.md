# UX Audit Report -- 2026-03-29

**Auditor**: UX Designer Agent
**Scope**: Full frontend audit -- all pages, components, i18n, design system consistency
**Methodology**: Static code analysis of every page under `src/frontend/src/app/` and every component under `src/frontend/src/components/`

---

## Executive Summary

The Vetara frontend is well-structured overall, with consistent use of shadcn/ui components, Tailwind spacing, CSS design tokens, proper `data-testid` coverage on most interactive elements, and a solid loading/error state pattern in dashboard pages. However, the audit uncovered several issues across i18n completeness, hardcoded strings, brand inconsistency, color token bypass, and accessibility gaps. The most impactful issues affect Arabic-speaking users (i18n gaps), search/SEO (help center not localized), and brand trust (inconsistent app name).

**Total issues found: 31**
- CRITICAL: 3
- HIGH: 10
- MEDIUM: 12
- LOW: 6

---

## CRITICAL Issues

### C1. Brand name inconsistency: "Veto" vs "Vetara"

**File**: `src/frontend/src/components/features/shell/Header.tsx` line 52
**Problem**: The main dashboard header displays "Veto" (truncated) while every other location (login, signup, sidebar, footer, portal, landing) says "Vetara".
**Impact**: Confuses users. A vet rushing between screens sees two different brand names. Damages trust and professionalism.
**Recommendation**: Change `<span>Veto</span>` to `<span>Vetara</span>` in Header.tsx.

### C2. Help Center is 100% hardcoded English -- 890 lines with zero i18n

**File**: `src/frontend/src/app/[locale]/help/page.tsx` (890 lines)
**Problem**: The entire Help Center (33 articles, section labels, search placeholder, all article content) is hardcoded in English. Zero `useTranslations()` calls. Despite being under the `[locale]` route, an Arabic user gets an entirely English help center.
**Impact**: Arabic-speaking vets in the UAE cannot use Help Center. This is the primary self-service support channel.
**Recommendation**: Extract all article titles, content, section labels, and UI strings to i18n messages. Short-term: at least extract UI chrome strings. Long-term: translate article content.

### C3. Profile page is 100% hardcoded English

**File**: `src/frontend/src/app/[locale]/(dashboard)/profile/ProfilePageClient.tsx`
**Problem**: Every string is hardcoded: "Profile", "View your account information", "Account Details", "Name", "Email", "Role", "Clinic", "Security", "Change Password", "Unable to load profile information. Please log in again."
**Impact**: Arabic and French users see an English-only profile page in a multilingual app. The profile page is a daily touchpoint.
**Recommendation**: Move all strings to i18n keys under a `profile` namespace.

## HIGH Issues

### H1. i18n key gaps -- 27 keys missing from French translation

**Details**: The following 27 keys exist in `en.json` but not in `fr.json`:
- `patients.search_placeholder_extended`
- `patients.form.sex`, `patients.form.select_sex`, `patients.form.sex_male`, `patients.form.sex_female`, `patients.form.sex_intact_male`, `patients.form.sex_intact_female`, `patients.form.sex_unknown`
- `patients.form.microchip`, `patients.form.microchip_optional`, `patients.form.microchip_placeholder`, `patients.form.microchip_hint`, `patients.form.errors.microchip_format`
- `landing.hero.social_proof_badge`
- `landing.testimonials.quote{1,2,3}.emirate`, `landing.testimonials.quote{1,2,3}.rating`
- `landing.sticky_cta.tagline`, `landing.sticky_cta.cta`
- `landing.exit_intent.email_placeholder`, `landing.exit_intent.cta`, `landing.exit_intent.success`
- `landing.footer_cta.headline`, `landing.footer_cta.cta`

**Impact**: French-speaking users will see raw i18n keys or empty strings in the patient form and landing page.
**Recommendation**: Add all missing keys to `fr.json`. Note: `ar.json` is only missing 1 key (`landing.footer.lang_fr`), which is acceptable.

### H2. Dashboard error page -- hardcoded English strings, no i18n

**File**: `src/frontend/src/app/[locale]/(dashboard)/error.tsx`
**Problem**: "An error occurred", "Something went wrong. Please try again...", "Try again" are all hardcoded.
**Impact**: Arabic users see English error messages during failures.
**Recommendation**: Use `useTranslations('errors')` for all three strings.

### H3. New Medical Record page -- multiple hardcoded English strings

**File**: `src/frontend/src/app/[locale]/(dashboard)/patients/[id]/records/new/page.tsx`
**Hardcoded strings**:
- "Patient not found." (line 46)
- "Back to Patients" (line 49)
- "New Medical Record" (line 73)
- "Record consultation details for {name}." (line 76)
- "{name}'s record" (line 66)

**Impact**: Arabic vets creating medical records see English UI text.
**Recommendation**: Move all strings to i18n.

### H4. Patients list page -- hardcoded pagination and count strings

**File**: `src/frontend/src/app/[locale]/(dashboard)/patients/PatientsPageClient.tsx`
**Hardcoded strings**:
- `'patient'` / `'patients'` (line 118) -- plural logic
- `"Previous"` (line 186)
- `"Page {currentPage} of {totalPages}"` (line 189)
- `"Next"` (line 200)

**Impact**: Arabic and French users see English pagination controls.
**Recommendation**: Use i18n with ICU plural syntax for patient count, and add pagination keys.

### H5. New Patient page -- hardcoded subtitle

**File**: `src/frontend/src/app/[locale]/(dashboard)/patients/new/page.tsx` line 31
**Hardcoded**: "Register a new patient and their owner."
**Impact**: Minor but breaks the i18n consistency.
**Recommendation**: Add an i18n key `patients.form.subtitle`.

### H6. Patient detail page -- hardcoded age calculation strings

**File**: `src/frontend/src/app/[locale]/(dashboard)/patients/[id]/page.tsx` lines 28-45
**Hardcoded**: "1 month", "months", "1 year", "years", "year", "month" -- all in English.
**Impact**: Arabic users see English age labels on the patient card, mixed with Arabic UI.
**Recommendation**: Use i18n with ICU plural syntax for age formatting.

### H7. StockItemForm -- hardcoded description strings

**File**: `src/frontend/src/components/features/stock/StockItemForm.tsx` line 99
**Hardcoded**: "Update the stock item details below." / "Fill in the details to add a new stock item."
**Impact**: English-only description in stock management form.
**Recommendation**: Add i18n keys `stock.form.edit_description` and `stock.form.add_description`.

### H8. ErrorState component defaults are English-only

**File**: `src/frontend/src/components/ui/error-state.tsx`
**Problem**: Default props `title = 'Something went wrong'`, `description = 'An error occurred while loading data.'`, `retryLabel = 'Retry'` are hardcoded English.
**Impact**: Any caller that does not explicitly pass translated strings shows English fallbacks. Since this is a reusable component, the blast radius is large.
**Recommendation**: Either require these props (no defaults) to force callers to pass translated strings, or accept i18n namespace as prop.

### H9. WeightChart uses hardcoded hex colors instead of CSS tokens

**File**: `src/frontend/src/components/features/patients/WeightChart.tsx` line 75-87
**Hardcoded hex values**: `#f0f0f0`, `#888`, `#e5e5e5`
**Impact**: The chart does not respect dark mode or theme changes. In dark mode, light gray grid lines and text will be invisible.
**Recommendation**: Use CSS custom properties or extract theme-aware color references.

### H10. Extensive use of raw Tailwind color classes instead of design tokens

**Scope**: 304 occurrences across 79 files using `text-stone-*`, `bg-stone-*`, `text-red-*`, `bg-red-*`, `text-amber-*`, `text-green-*`, `text-yellow-*`.
Additional: 62 occurrences of `bg-blue-*`, `text-blue-*`, `text-purple-*`, `text-orange-*` across 32 files.
Plus 127 occurrences of `bg-white` across 78 files (should be `bg-card` or `bg-background`).

**Impact**: These colors bypass the design token system defined in `globals.css`. They will not adapt to dark mode. They create visual inconsistency if the primary palette ever changes.
**Nuance**: The landing page (`page.tsx`) legitimately uses `stone-*` for a distinct marketing design. But dashboard components (`StockTable`, `StockMovementTable`, `CalendarHeader`, `HealthAlertPanel`, etc.) should use semantic tokens (`text-foreground`, `text-muted-foreground`, `bg-destructive`, `bg-muted`, etc.).
**Recommendation**: Audit each usage. Replace dashboard/app occurrences with semantic tokens. Landing page can keep direct Tailwind colors since it has its own visual identity.

## MEDIUM Issues

### M1. No error boundary for auth routes

**Observation**: `(auth)/` has a `loading.tsx` but no `error.tsx`. If login/signup throws, the user gets the Next.js default error page.
**Recommendation**: Add `(auth)/error.tsx` with proper styling and i18n.

### M2. Dashboard greeting function only supports English and Arabic

**File**: `src/frontend/src/app/[locale]/(dashboard)/dashboard/page.tsx` lines 17-33
**Problem**: `getGreeting()` handles `ar` and defaults to English. French is not handled.
**Recommendation**: Add French greetings ("Bonjour", "Bon apres-midi", "Bonsoir").

### M3. Patient form has both "gender" and "sex" fields -- confusing UX

**File**: `src/frontend/src/components/features/patients/PatientForm.tsx`
**Problem**: The form has both a "Gender" dropdown (Male/Female/Unknown) and a "Sex" dropdown (Male/Female/Intact Male/Intact Female/Unknown). For a vet in a hurry, two fields that look almost identical is confusing.
**Recommendation**: Consult PO. In veterinary practice, "Sex" (including intact/neutered status) is typically the only relevant field. Consider removing "Gender" or merging the two.

### M4. Patient detail page -- no loading skeleton for tabs content

**Observation**: While the page has a loading state for the patient header, the medical records, vaccinations, and prescriptions tabs show no skeleton/spinner during their individual loading phases. `isLoadingRecords` is tracked but MedicalRecordsList receives it as `isLoading` -- good. However, vaccinations and prescriptions tabs have no loading states.
**Recommendation**: Add loading skeletons to vaccinations and prescriptions tabs.

### M5. Tabs on patient detail page -- horizontal scroll not handled for mobile

**File**: `src/frontend/src/app/[locale]/(dashboard)/patients/[id]/page.tsx` lines 370-393
**Problem**: 5 tabs ("Medical Records", "Prescriptions", "Vaccinations", "Health Alerts", "Weight") in a horizontal row. On a 375px screen, these will overflow or wrap poorly.
**Recommendation**: Add `overflow-x-auto` and `whitespace-nowrap` to the tabs container, or use a scrollable tab pattern.

### M6. Sidebar is hidden on all screens below `md` breakpoint but dashboard nav uses `lg`

**Observation**: The `Sidebar` component uses `md:flex` (768px) to show. But the Header component uses `lg:flex` (1024px) for desktop nav tabs. This means between 768-1024px, the user has no visible sidebar AND no visible nav tabs -- they must use the hamburger menu.
**Impact**: Tablet users (common in vet clinics with mounted tablets) have a suboptimal experience.
**Recommendation**: Align breakpoints. Either show sidebar at `md` (it currently does, but the header hides desktop nav until `lg`). The sidebar's `md:flex` and header's `hidden lg:flex` are inconsistent -- the sidebar renders but the header nav does not, creating a confusing dual-nav between 768-1024px. Actually, reviewing the dashboard layout, there is NO sidebar in the layout -- only the Header. The Sidebar component exists but is never mounted in the dashboard layout. This means the `Sidebar` component is dead code.

### M7. Landing page "Blog" link text is hardcoded

**File**: `src/frontend/src/app/[locale]/page.tsx` lines 164-165, 191
**Hardcoded**: The text "Blog" in both desktop nav and mobile nav links.
**Recommendation**: Add a `landing.nav.blog` i18n key.

### M8. Missing `aria-invalid` on PatientForm inputs

**File**: `src/frontend/src/components/features/patients/PatientForm.tsx`
**Problem**: None of the input fields have `aria-invalid` attributes when validation errors are present. The Login and Signup forms correctly use `aria-invalid` and `aria-describedby`, but PatientForm does not.
**Impact**: Screen readers cannot announce invalid fields to visually impaired users.
**Recommendation**: Add `aria-invalid={!!errors.fieldName}` and `aria-describedby` to all form inputs.

### M9. Calendar aria-labels are hardcoded English

**File**: `src/frontend/src/components/features/calendar/CalendarHeader.tsx` lines 121-125
**Hardcoded**: `aria-label="Previous"`, `aria-label="Next"`
**Impact**: Screen readers announce English labels regardless of locale.
**Recommendation**: Pass translated strings for aria-labels.

### M10. No focus trap or keyboard navigation in mobile sidebar sheet

**Observation**: The mobile sidebar uses shadcn `Sheet`, which should handle focus trapping via Radix. However, there is no visible focus ring styling on nav items inside the sheet.
**Recommendation**: Verify focus management works correctly on mobile. The SidebarNavItem does have `focus-visible:ring-2`, which is good.

### M11. "fr" language key missing from Arabic translations

**File**: `messages/ar.json`
**Missing key**: `landing.footer.lang_fr`
**Impact**: If a French language switcher option is shown in the Arabic footer, it will display raw key.
**Recommendation**: Add the missing key.

### M12. `bg-white` used instead of `bg-card` or `bg-background` in dashboard components

**Scope**: 127 occurrences across 78 files.
**Problem**: `bg-white` ignores the design token system. If dark mode is enabled, white backgrounds will create jarring contrast.
**Impact**: Dark mode will be broken across nearly every component.
**Recommendation**: Replace `bg-white` with `bg-card` (for card-like surfaces) or `bg-background` (for page-level backgrounds) throughout dashboard components. Landing page is excluded since it intentionally uses a white-only design.

## LOW Issues

### L1. Page metadata titles are hardcoded English

**Files**: Multiple `page.tsx` files use `metadata.title` with hardcoded English ("Patients", "Billing", "Stock", "Appointments", "Messages", "Settings", "Profile").
**Impact**: Browser tabs show English titles regardless of locale.
**Recommendation**: Use `generateMetadata()` with `getTranslations()` for page titles, as already done in the landing page and signup page.

### L2. `page-container.tsx` always emits `data-testid="page-container"`

**File**: `src/frontend/src/components/ui/page-container.tsx`
**Problem**: The PageContainer always uses the same testid "page-container" regardless of context. Callers pass their own `data-testid` via props but the component also adds its own, leading to potential test confusion (two testids on same element via prop spreading).
**Recommendation**: Remove the default `data-testid` from PageContainer and let callers provide it.

### L3. Sidebar component exists but appears unused in dashboard layout

**File**: `src/frontend/src/components/features/shell/Sidebar.tsx`
**Observation**: The dashboard layout (`(dashboard)/layout.tsx`) only renders `<Header />`. The `Sidebar` component is imported nowhere in the layout. Only `MobileSidebarContent` is used (inside Header's Sheet).
**Impact**: The full `Sidebar` component (desktop version) is dead code -- 265 lines of unused component.
**Recommendation**: Either remove the unused `Sidebar` export or integrate it into the layout if a sidebar is planned.

### L4. `mr-1` used instead of logical `me-1` in one place

**File**: `src/frontend/src/components/features/patients/PatientForm.tsx` line 452
**Hardcoded**: `mr-1.5` on the Loader2 spinner.
**Impact**: In RTL (Arabic) mode, the spinner appears on the wrong side of the text.
**Recommendation**: Change to `me-1.5` (margin-end) for RTL support. The rest of the codebase correctly uses `me-*` and `ms-*`.

### L5. Inconsistent empty state patterns

**Observation**: The patients list uses the reusable `EmptyState` component from onboarding. But other pages (vaccinations tab, prescriptions tab in patient detail) use inline `<p className="text-muted-foreground text-[13px] py-8 text-center">` for empty states. No icon, no CTA, no consistent pattern.
**Recommendation**: Adopt the `EmptyState` component pattern across all empty states for visual consistency.

### L6. `appointments.search_aria` and `appointments.filter_by_status` keys exist in FR and AR but not EN

**Impact**: Very minor. These 2 keys exist in `fr.json` and `ar.json` but not `en.json`. If referenced in code, English users would see raw keys.
**Recommendation**: Either add them to `en.json` or remove them from FR/AR if unused.

## Design System Consistency Summary

### What works well

- **shadcn/ui adoption**: All form inputs, buttons, cards, dialogs, selects, badges, sheets use shadcn/ui components. No raw HTML inputs detected.
- **CSS token system**: `globals.css` defines a comprehensive token set (primary, secondary, accent, muted, destructive, success, warning, info, chart colors). Both light and dark mode variants exist.
- **Typography**: Consistent use of `text-[22px] font-bold` for page titles, `text-[13px]` for body text, `text-[11px]` for table headers. Manrope font is set as the sans-serif default.
- **Spacing**: Consistent use of Tailwind spacing scale (gap-6, p-6, space-y-6).
- **data-testid coverage**: Excellent on most pages and components. Dashboard, patients, appointments, billing, stock, auth, settings, messaging -- all have comprehensive testids.
- **Loading states**: Dashboard and auth routes have proper skeleton-based loading states.
- **Error states**: Reusable `ErrorState` component exists. Patients page uses it correctly.
- **RTL support**: Good use of `me-*`, `ms-*` logical properties and `ltr:/rtl:` variants in navigation.
- **Page title pattern**: Consistent "pill + title" visual pattern across all pages (the small `bg-primary rounded-full` bar before h1 text).

### What needs improvement

- **bg-white vs bg-card**: 127 occurrences bypass tokens.
- **Raw Tailwind colors**: 366 occurrences of non-token colors across 79+ files.
- **Hardcoded hex**: 5 occurrences in WeightChart.
- **i18n coverage**: 27 keys missing from French, ~50+ hardcoded English strings in dashboard pages.
- **Brand consistency**: "Veto" in header vs "Vetara" everywhere else.
